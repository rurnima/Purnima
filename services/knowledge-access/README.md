# Purnima Knowledge Access

This service is the isolated retrieval capability for Purnima. It does not add a Search screen and does not implement persistent personal learning.

## Current implementation

- Cloudflare Worker endpoints: `POST /v1/knowledge/ingest` and `POST /v1/knowledge/search`.
- Workers AI multilingual embeddings via `@cf/baai/bge-m3`.
- Vectorize stores chunk embeddings and metadata; search is filtered by the authenticated device's canonical ID.
- Authentication verifies short-lived RS256 bearer tokens against Purnima Device Auth's fixed issuer and audience. Its public signing keys are fetched over HTTPS from the fixed JWKS endpoint with a descriptive application User-Agent; users configure no URLs or secrets. The canonical scope is the signed `sub` claim; the client cannot choose its own tenant/user ID.
- Chunking is bounded; ingestion reports accepted indexing work and callers must allow for Vectorize's eventual query visibility.

## Development resources provisioned

- Vectorize index: `purnima-knowledge-access-dev`
- Index configuration: 1024 dimensions, cosine distance.
- Metadata filter index: `userId` (string), verified present.
- Workers AI model `@cf/baai/bge-m3` was called successfully with Bengali text and returned shape `[1, 1024]`.

## Authentication integration

The issuer and audience are fixed in the service code; the public signing key endpoint is called directly over HTTPS:
- JWKS: `https://purnima-auth.purnima.workers.dev/.well-known/jwks.json`
- Issuer: `https://purnima-auth.purnima.workers.dev`
- Audience: `purnima-api`

The Device Auth implementation is isolated in PR #13. It creates an installation identity automatically, keeps the P-256 private key in Android Keystore, and issues short-lived RS256 tokens after one-time challenge proof. The signing key is generated by the Worker and persisted in the dedicated D1 auth-key table. Users do not paste tokens, API keys, issuer URLs, or credentials.

This is a device identity rather than an email/phone/Google account. Reinstalling the app or switching devices creates a new identity; account recovery and multi-device linking are separate work.

## API

- `POST /v1/knowledge/ingest`: authenticated JSON body `{ documentId, title, text }`.
- `POST /v1/knowledge/search`: authenticated JSON body `{ query, limit? }`.
- `GET /health`: liveness only; exposes no account data.

## Security and scope

- User scope comes only from the verified RS256 `sub` claim.
- Vector metadata filtering is not a substitute for authorization; every request is authenticated first.
- No API keys or LiveKit credentials belong in Android resources or the repository.
- This feature does not change Home, Chat, Voice UI, Agent Runtime, or D1 learning records.
